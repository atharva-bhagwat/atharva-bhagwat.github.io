Data is small, feedback is instant, and a mistake costs seconds. Everything in the twelve stages was practice for the habits that make a cluster usable later:</p><div class="q-table-wrap"><table class="q-table"><thead><tr><th>Habit you built</th><th>Why the cluster needs it</th></tr></thead><tbody><tr><td>Isolated environment plus <code>environment.yml</code></td><td>You rebuild the exact same Python on the cluster in one command.</td></tr><tr><td>Scripts like <code>src/make_figures.py</code></td><td>A cluster job runs a script, not a notebook you click through.</td></tr><tr><td>Relative paths from a project root</td><td>The same code runs in a different folder on a different machine.</td></tr><tr><td>Functions with parameters</td><td>One script can process any sample or setting you hand it.</td></tr><tr><td>Raw data never edited, results regenerated</td><td>Jobs can be re-run safely, and you always know where an output came from.</td></tr><tr><td>Reading the last line of an error</td><td>Failed jobs leave you a log file full of tracebacks. You already know how to read one.</td></tr></tbody></table></div><h3>When do you actually need HPC?</h3><p>Not for this dataset: four thousand rows fit on any laptop. Develop small, then scale up when one of these happens:</p><ul><li><strong>Memory:</strong> you hit <code>MemoryError</code>, or your laptop starts crawling because the data does not fit in RAM.</li><li><strong>Time:</strong> one run takes hours, or you need to repeat it for many samples or many parameter settings.</li><li><strong>Hardware:</strong> you need many cores at once, or a GPU.</li></ul><aside class="q-callout is-trap"><strong class="q-callout-title">Never run heavy work on a login node</strong><p>When you log in, you land on a shared machine used by everyone to edit files and submit jobs. Anything big belongs in a job that the scheduler (Slurm) places on a compute node. Start with an interactive job to try things, and a batch job once it works.</p></aside><h3>The same project, on the cluster</h3><ol><li><strong>Get access.</strong> Request an account and read how resources are allocated: <a href="https://crc-pages.pitt.edu/user-manual/getting-started/getting-started-step1-account/" target="_blank" rel="noopener">getting an account</a> and <a href="https://crc-pages.pitt.edu/user-manual/keystone/requesting/" target="_blank" rel="noopener">requesting resources</a>.</li><li><strong>Log in.</strong> Use a terminal (<a href="https://crc-pages.pitt.edu/user-manual/getting-started/terminal/" target="_blank" rel="noopener">SSH</a>) or the browser portal (<a href="https://crc-pages.pitt.edu/user-manual/getting-started/open-ondemand/" target="_blank" rel="noopener">Open OnDemand</a>). OnDemand also offers <a href="https://crc-pages.pitt.edu/user-manual/getting-started/quickstart-python-ondemand/" target="_blank" rel="noopener">Python and Jupyter sessions</a> if you want a notebook on a compute node.</li><li><strong>Bring your code.</strong> Put the project in a Git repository on your laptop, then <code>git clone</code> it on the cluster. Code travels through Git; it keeps a history and avoids "which copy is newest?".</li><li><strong>Bring your data.</strong> Large files go through a transfer tool, not Git. See <a href="https://crc-pages.pitt.edu/user-manual/data-management/file-transfer-methods/" target="_blank" rel="noopener">file transfer</a> (<a href="https://crc-pages.pitt.edu/user-manual/data-management/file-transfer-methods/globus/" target="_blank" rel="noopener">Globus</a> is the usual choice) and the <a href="https://crc-pages.pitt.edu/user-manual/data-management/file-systems/" target="_blank" rel="noopener">file systems</a> page to decide where files should live. Big temporary files belong in <a href="https://crc-pages.pitt.edu/user-manual/slurm/scratch-storage/" target="_blank" rel="noopener">scratch</a>.</li><li><strong>Rebuild the environment.</strong> Load conda or Python the way the <a href="https://crc-pages.pitt.edu/user-manual/applications/python/" target="_blank" rel="noopener">Python page</a> describes, then recreate yours: <code>conda env create -f environment.yml</code>. This is why you froze it in Stage 12.</li><li><strong>Test on a small slice.</strong> Ask for a short <a href="https://crc-pages.pitt.edu/user-manual/slurm/interactive-jobs/" target="_blank" rel="noopener">interactive job</a>, run your script on a few rows, and fix errors where you can see them.</li><li><strong>Submit a batch job.</strong> Write a short job script and hand it to Slurm (<a href="https://crc-pages.pitt.edu/user-manual/slurm/batch-jobs/" target="_blank" rel="noopener">batch jobs</a>).</li><li><strong>Check, then copy results home.</strong> Read the log, confirm the outputs look right, and copy <code>results/</code> back to your laptop for figures and writing.</li></ol><h3>A job script</h3><p>A batch script is a shell script with <code>#SBATCH</code> lines that tell Slurm what to reserve. The names of clusters and partitions, and sensible memory and time requests, are specific to your group; copy real values from the manual rather than from this sketch.</p><div class="qcode"><div class="qcode-bar"><span class="qcode-name">run_make_figures.sh</span><button class="qcopy" type="button">Copy</button></div><pre><code><span class="ch">#!/bin/bash</span>
<span class="c1">#SBATCH --job-name=make-figures</span>
<span class="c1">#SBATCH --cluster=CLUSTER_NAME        # placeholder: copy real values from the manual</span>
<span class="c1">#SBATCH --partition=PARTITION_NAME    # placeholder</span>
<span class="c1">#SBATCH --nodes=1</span>
<span class="c1">#SBATCH --cpus-per-task=4</span>
<span class="c1">#SBATCH --mem=16G</span>
<span class="c1">#SBATCH --time=01:00:00</span>
<span class="c1">#SBATCH --output=logs/%x-%j.out       # %x = job name, %j = job id</span>

<span class="c1"># 1. make the same Python the same way you did on your laptop</span>
<span class="c1">#    (how to load conda or Python on the cluster is on the manual's Python page)</span>
conda<span class="w"> </span>activate<span class="w"> </span>pandas-quest

<span class="c1"># 2. run from the project root so relative paths behave</span>
<span class="nb">cd</span><span class="w"> </span><span class="s2">"</span><span class="nv">$SLURM_SUBMIT_DIR</span><span class="s2">"</span>

<span class="c1"># 3. run the script, not a notebook</span>
python<span class="w"> </span>src/make_figures.py</code></pre></div><p>Submit it and keep an eye on it:</p><div class="qcode"><div class="qcode-bar"><span class="qcode-name">terminal on the cluster</span><button class="qcopy" type="button">Copy</button></div><pre><code>mkdir<span class="w"> </span>-p<span class="w"> </span>logs
sbatch<span class="w"> </span>run_make_figures.sh<span class="w">     </span><span class="c1"># prints: Submitted batch job 12345678</span>
squeue<span class="w"> </span>--me<span class="w">                    </span><span class="c1"># what is queued or running</span>
sacct<span class="w"> </span>-j<span class="w"> </span><span class="m">12345678</span><span class="w">              </span><span class="c1"># what happened, after it finishes</span>
scancel<span class="w"> </span><span class="m">12345678</span><span class="w">               </span><span class="c1"># stop it</span></code></pre></div><aside class="q-callout is-note"><strong class="q-callout-title">Reading a failed job</strong><p>The log file in <code>logs/</code> is your traceback. Open it and go to the bottom, exactly like Stage 2. A job killed for time or memory says so: ask for a little more of what ran out, not ten times more. Smaller requests usually start sooner.</p></aside><h3>Habits that make cluster work painless</h3><ul><li><strong>Develop small, run big.</strong> Add a small slice or a <code>--sample</code> option to your script so you can test in seconds.</li><li><strong>Many similar tasks?</strong> Do not write a loop in one long job; use a <a href="https://crc-pages.pitt.edu/user-manual/slurm/job-arrays/" target="_blank" rel="noopener">job array</a> so each sample runs on its own.</li><li><strong>Keep sessions alive.</strong> <a href="https://crc-pages.pitt.edu/user-manual/tips/persist-sessions/" target="_blank" rel="noopener">tmux and nohup</a> let long-running work survive a dropped connection.</li><li><strong>Edit comfortably.</strong> VS Code can work on cluster files directly: see the <a href="https://crc-pages.pitt.edu/user-manual/slurm/vscode/" target="_blank" rel="noopener">VS Code page</a>.</li><li><strong>Record what you ran.</strong> Commit the job script, the <code>environment.yml</code> and the README. Next month, they are your memory.</li><li><strong>Stuck?</strong> Check <a href="https://crc-pages.pitt.edu/user-manual/faq/" target="_blank" rel="noopener">Common Problems</a> and the <a href="https://crc-pages.pitt.edu/user-manual/" target="_blank" rel="noopener">main user manual</a>, then ask the support team with the job ID and the last lines of the log.</li></ul><p>The full documentation for everything above lives in the <a href="https://crc-pages.pitt.edu/user-manual/" target="_blank" rel="noopener">CRCD User Manual</a>.</p></div></section><nav class="q-nav" aria-label="Previous and next"><a class="q-nav-link is-prev" href="/articles/intro-to-python-biosci/ship-it"><span class="q-nav-dir">Back</span><span class="q-nav-name">Ship It</span></a><a class="q-nav-link is-next" href="/articles/intro-to-python-biosci/certificate"><span class="q-nav-dir">Next</span><span class="q-nav-name">Summit register</span></a></nav>
